- 対象バージョン: 0.6.15 のリリース直後（2026-11-05）の観察
- 着手するときは、該当する設計書・要件定義書を先に読み、必要なら更新する（要件定義書が最優先）
- 完了した項目は削除せず、「対応済み」へ移し、対応したバージョンと CHANGELOG の節を書く

> このファイルは `.doc_structure.yaml` の索引対象（`spec` / `design` / `plan` / `mcp-guide`）の外に置いている。ルールや仕様の検索インデックスには載らない。

## 検索ツール（`search_code` / `search_files_without_pattern` / `find_files`）

検索ツールを変更するときは、先に `design/DES-104_search_symbol_tools_enhancement_design.md`（TBD-006、§5.1、§9.1）と `spec/REQ-003_Core_Features_Requirements.md` の search_code を読む。破壊的変更は次のマイナーバージョンに載せ、CHANGELOG に「挙動の変更」と明記する。

### B-1: 単独の `*` が `/` をまたぐ（破壊的変更）

- **現状**: `FileSearcher.wildcardToRegex` が `*` を `.*` に変換するため、`Sources/*.swift` が `Sources/Tools/Foo.swift` にも一致する
- **問題**: 標準的な glob（gitignore、ripgrep）と異なり、意図しない範囲が対象になる
- **提案**: `*` は `/` 以外の任意の文字列、`**` は `/` をまたぐ任意の文字列にする
- **影響**: `*/FileSystem/*.swift` のように、現在 `*` が `/` をまたぐ前提で書かれたパターンの結果が変わる。破壊的変更のため、次のマイナーバージョンに載せる
- **関連**: B-2 と同時に変えると、パターン仕様の変更を 1 回にまとめられる

### B-2: glob の大文字小文字の扱い

- **現状**: 内容検索の正規表現は大文字小文字を区別する（`options: []`）が、glob の一致は区別しない（`.caseInsensitive`）
- **問題**: 両者が食い違い、大文字小文字を区別するファイルシステムで `foo.swift` が `Foo.swift` にも一致する
- **提案**: glob は既定で区別する。区別しないオプション `ignore_case`（真偽値）を `include_patterns` / `exclude_patterns` に追加する。内容検索の正規表現にも効かせるか（`grep -i` 相当）は未決
- **影響**: 既定の変更を伴うため、B-1 と同じく次のマイナーバージョンに載せる

### B-3: 応答サイズ

- **現状**: `match_detail` は、テキストと構造化 JSON（`--- structured ---`）で同じマッチを二重に返す。既定の上限（100 件）でも約 3 万文字になる。マッチ 1 件あたりの大半は絶対パスである
- **問題**: クライアントの出力上限に近い。一般語の検索では、`limit` を絞らないと応答が大きい
- **提案**: パスをプロジェクトルートからの相対にする。出力モードで構造化結果を省略可能にする
- **影響**: 出力形式の変更で、既存の呼び出し側（AI）に影響する。DES-104 と REQ-003 の更新が必要

### B-4: `find_files` の説明が「Swift files」

- **現状**: 実装は `.swift` のみが対象（`Package.swift` は出るが、`README.md` などは出ない）
- **提案**: ツールの説明文に、対象が `.swift` のみであることを明記する。説明文の変更のみで足りる

### B-5: ディレクトリ名だけのパターン

- **現状**: `Tests` のようなディレクトリ名だけのパターンは、対象がファイルのため一致しない。`Tests/**` か `**/Tests/**` と書く必要がある
- **未決**: 仕様として説明に残すか、gitignore 流にディレクトリも一致させるか

## 運用・リポジトリ

### O-1: リモートの `develop` ブランチ（確認待ち）

- **確定していること**: 0.6.15 の反映後、`git ls-remote --heads origin` が `main` だけを返した。数時間前には、`origin/develop` に 0.6.15 のバージョン更新が入っていた
- **不確実なこと**: 削除の原因（意図的な削除か、GitHub の「マージ後にブランチを自動削除」の設定か）
- **影響の可能性**: 後者なら、リリースのたびに `develop` が消える。`.github/workflows/version_check.yml` と `close-issues-on-develop.yaml` が `develop` を前提にしている可能性がある
- **次の一手**: 原因を確認する。設定なら、`develop` を保護するか、運用を見直す

### O-2: `make register-claude` はリポジトリ内のリリースビルドを登録する

- **現状**: `.build/release/Swift-Selena` を登録する。ビルドし直さないと、古いバイナリのまま動く（0.6.15 の確認時に、10/30 のビルドが登録されていた）。`--version` が無い古いビルドは、見分けにくい
- **提案**: 配布版（brew）を使う運用に変えるなら、`DEVELOPMENT.md` の開発用／配布版の使い分けを見直す。登録時にバージョンを表示する、などの案もある

### O-3: タグ検証 CI（`release_tag_check.yml`）の廃止

- **経緯**: 0.6.14 のタグで 1 回だけ失敗した。ローカルと新規クローンでは、同じ検証が通り、原因は特定できなかった（`grep -q` と `pipefail` の SIGPIPE 競合などの仮説はあるが、未確認）。CI が問題の解決ではなく問題そのものになったため、0.6.15 で廃止した
- **現在の運用**: `scripts/verify_release_tag.sh` をローカルで実行する（CLAUDE.md のリリース手順 7）
- **方針**: CI に戻す場合は、失敗の原因を特定してから、あらためて判断する
